# 3. Migrating Your On-Prem GCDS Config

Moving your existing production `sync-config.xml` from a Windows Server or Linux VM into `gcds-in-the-cloud` requires **no rule rewrites**—only a quick pre-flight check and a zero-risk dry-run comparison before turning off your old scheduled task.

---

## What You Can Leave Behind on the Old Server

When copying `sync-config.xml` off your existing GCDS machine, you **do NOT** need to export or copy:
* ❌ `~/.java/.userPrefs` or Windows Registry Java Preference keys
* ❌ `upgrade-config -exportkeys` keyfiles *(our container re-encrypts `<authPassword>` from Secret Manager and injects a synthetic `<oauthRefreshToken>` in RAM automatically on every boot!)*
* ❌ Human Super Admin OAuth authorizations *(no clicking "Authorize Now")*
* ❌ Corporate proxy settings inside `sync-config.xml` *(JVM flags automatically route Google API calls through `127.0.0.1:8443` while letting LDAPS talk directly over VPC/VPN)*

---

## Step 1: Pre-Flight Audit of Your Existing `sync-config.xml`

Open a copy of your production `sync-config.xml` in a text editor (or GCDS Configuration Manager) and verify four items:

### 1. Active Directory Hostname & LDAPS (`636` / `3269`)
Check `<ldapConfiguration>`:
* Ensure `<hostName>` points to a DNS name resolvable from your GCP VPC (e.g., `dc01.corp.example.com` or `rodc-gcp.corp.example.com`—see [Guide 1](1.-Connecting-Cloud-Run-to-Active-Directory)).
* Ensure `<connectMethod>` uses **`SSL`** (`LDAPS`, port `636` or Global Catalog `3269`) rather than plaintext `STANDARD` (`389`) when traversing a VPC or Cloud VPN.

### 2. Log File Paths (`<logFileName>`)
* No manual edit required! Even if your XML still contains `<logFileName>C:\GCDS\logs\sync.log</logFileName>`, `entrypoint.sh` automatically rewrites `<logFileName>` in RAM to `/dev/shm/gcds-sync.log` and prints the full structured log to **Cloud Logging** on exit.

### 3. External CSV / Mapping File References (Rare)
* Most GCDS deployments store all exclusion rules and search queries inline inside `sync-config.xml`. If your config references an external local file path (such as a legacy password/mapping CSV on `D:\scripts\...`), inline those rules into the XML before uploading.

### 4. Legacy SMTP Notification Settings (Optional)
* If `<notification>` points to an on-premises internal-only SMTP relay (`10.x.x.x:25`) that won't be reachable (or needed) in GCP, either disable email notifications inside GCDS Configuration Manager -> **Notifications** and use native **Cloud Monitoring Alerts** instead (see [Guide 4](4.-Day-2-Operations-and-Scheduling)), or verify your VPC allows port `587`/`25` to your relay.

---

## Step 2: Deploy `gcds-in-the-cloud` & Upload Your Config

1. Clone the repository and run the turnkey deployment script:
   ```bash
   git clone https://github.com/jay0lee/gcds-in-the-cloud.git
   cd gcds-in-the-cloud

   export PROJECT_ID="your-gcp-project"
   export REGION="us-central1"
   export VPC_NETWORK="your-ad-vpc"
   export VPC_SUBNET="your-ad-subnet"

   ./deploy/cloud-run/deploy.sh
   ```
2. Store your Active Directory bind password in **Secret Manager**:
   ```bash
   printf '%s' 'YOUR_ACTUAL_AD_BIND_PASSWORD' | \
     gcloud secrets versions add gcds-ldap-password --data-file=- --project="$PROJECT_ID"
   ```
   *(If your AD uses an internal AD CS Root CA for LDAPS, also attach `AD_CA_CERT_PEM` as shown in [Guide 1](1.-Connecting-Cloud-Run-to-Active-Directory#trusting-your-internal-active-directory-ldaps-certificate-ad_ca_cert_pem)).*
3. Upload your `sync-config.xml` to the versioned GCS bucket:
   ```bash
   gcloud storage cp /path/to/your/sync-config.xml \
     "gs://${PROJECT_ID}-gcds-configs/sync-config.xml"
   ```

## Step 3: Side-by-Side Dry-Run Verification (Zero Workspace Mutations)

By default, `deploy.sh` sets `SYNC_MODE=simulate` (omitting `-a` on `sync-cmd`), meaning **nothing in Google Workspace is modified**.

1. Trigger a simulation run on Cloud Run:
   ```bash
   gcloud run jobs execute gcds-runner \
     --region="$REGION" \
     --project="$PROJECT_ID" \
     --wait
   ```
2. Inspect the logs in **Google Cloud Console -> Cloud Run -> Jobs -> `gcds-runner` -> Logs** (or via CLI):
   * Confirm `go-oauth-proxy` logged `served synthetic 3LO OAuth response` for `/token` and `200` responses on `admin.googleapis.com`.
   * Review GCDS's **Proposed Changes Summary** at the bottom of the log:
     * Compare the proposed creates/modifications/suspensions against a simultaneous `sync-cmd -c sync-config.xml` simulation on your existing on-prem server.
     * Both summaries should match **100%** (typically `0 changes` right after an on-prem sync run!).

---

## Step 4: Cutover & Decommission Legacy Credentials

Once your Cloud Run dry-run matches your on-prem server:

1. **Disable the On-Premises Job**: Disable the Windows Task Scheduler task (or comment out the Linux `crontab` entry) on your old GCDS server.
2. **Run One Interactive Apply in Cloud Run**:
   ```bash
   gcloud run jobs execute gcds-runner \
     --region="$REGION" \
     --project="$PROJECT_ID" \
     --update-env-vars="SYNC_MODE=apply" \
     --wait
   ```
3. **Enable Scheduled Syncs**: Set up Cloud Scheduler ([Guide 4](4.-Day-2-Operations-and-Scheduling)).
4. **Revoke the Old Human 3-Legged OAuth Token**:
   * In `admin.google.com` -> **Security -> Access and data control -> API controls -> App access control** (or the Super Admin's `myaccount.google.com/permissions`), **revoke** the legacy *"Google Cloud Directory Sync"* 3-legged OAuth grant so the old server's `sync-config.xml` token can never be abused.
