# 1. Connecting Cloud Run to Active Directory

When GCDS ran on a Windows or Linux VM inside your corporate data center, it sat right next to your **Active Directory Domain Controllers (DCs)** on the local LAN.

When you move GCDS to **Google Cloud Run Jobs**, the sync container runs inside Google Cloud and connects outbound to your private network using **Cloud Run Direct VPC Egress**. That raises the most important architectural question of the migration:

> **How should the running Cloud Run Job securely reach your Active Directory LDAP / LDAPS server?**

> **Security Rule #1**: **Never** expose Active Directory ports (`389`, `636`, `3268`, `3269`) to the public internet via port-forwarding. Always use private RFC 1918 routing + **LDAPS (`TCP 636` or Global Catalog `TCP 3269`)**.

---

## Comparing the 4 Active Directory Connectivity Options

| Architecture | Latency for Paged LDAP Queries | Resilience to ISP / WAN Blips | Infra Complexity | Best Fit |
| :--- | :--- | :--- | :--- | :--- |
| **Option A: HA Cloud VPN + Direct VPC Egress** | Medium (WAN RTT per LDAP page) | Depends on VPN uptime | **Low** (no extra VMs) | Small-to-mid directories (<25k objects) or orgs with existing Cloud VPN. |
| **Option B: AD Replica DC or Read-Only DC (RODC) in GCE** | **Sub-millisecond** (same GCP region) | **High** (syncs succeed even if WAN VPN drops) | Medium (1 small Windows GCE VM) | Large directories (25k–500k+ objects), multi-site orgs, or strict on-prem firewall policies. |
| **Option C: Google Cloud Managed Microsoft AD** | **Sub-millisecond** | **High** (Google-managed SLA) | Low–Medium | Orgs running cloud-first AD in GCP or migrating AD off-prem. |
| **Option D: Cloud Interconnect (Dedicated / Partner)** | Low | Very High | Enterprise | Enterprises already connected to GCP via Interconnect. |

---

## Option A: HA Cloud VPN to On-Premises Active Directory

If your Domain Controllers live strictly on-premises (or in AWS/Azure), connect your GCP VPC to your corporate firewall (Palo Alto, Fortinet, Cisco, pfSense, AWS Virtual Private Gateway) using **HA Cloud VPN** (IPsec with BGP via Cloud Router).

```text
[On-Premises LAN]                          [Google Cloud VPC]
┌──────────────────────┐    IPsec Tunnel   ┌───────────────────────────────────────┐
│ AD Domain Controller │◄═════════════════►│ Cloud VPN Gateway + Cloud Router      │
│ dc01.corp.example.com│   TCP 636 / 3269  │                  ▲                    │
│ (10.10.1.10)         │                   │                  │ Direct VPC Egress  │
└──────────────────────┘                   │         [Cloud Run Job: GCDS]         │
                                           └───────────────────────────────────────┘
```

### Checklist for Option A
1. **Firewall Rules (On-Prem & GCP Egress)**:
   * Allow **TCP `636`** (LDAPS) and/or **TCP `3269`** (Global Catalog LDAPS, required if syncing across a multi-domain AD forest) from your Cloud Run Direct VPC Egress subnet CIDR (`e.g., 10.200.0.0/26`) to your Domain Controller IPs.
   * Allow **UDP/TCP `53`** to your AD DNS servers if using Cloud DNS forwarding.
2. **Cloud DNS Private Forwarding Zone (Recommended for LDAPS)**:
   * LDAPS validates the X.509 certificate's Subject Alternative Name (e.g., `dc01.corp.example.com`)—connecting by raw IP (`10.10.1.10`) will fail TLS hostname verification unless the IP is in the cert SAN.
   * Create a **Cloud DNS Forwarding Zone** for `corp.example.com` attached to your VPC pointing to your internal AD DNS IPs:
     ```bash
     gcloud dns managed-zones create corp-ad-dns \
       --dns-name="corp.example.com." \
       --visibility="private" \
       --networks="your-ad-vpc" \
       --forwarding-targets="10.10.1.10,10.10.1.11" \
       --private-forwarding-targets="10.10.1.10,10.10.1.11"
     ```

## Option B: Running an Active Directory RODC (or Replica DC) in Google Cloud

For organizations with **large directories** or **strict security boundaries**, placing a small Compute Engine VM (`e2-medium` or `n2-standard-2`) running Windows Server Core as a **Read-Only Domain Controller (RODC)** inside your GCP VPC is often the cleanest long-term architecture.

```text
[On-Premises AD]              [Google Cloud VPC (us-central1)]
┌──────────────────┐   VPN /  ┌────────────────────────┐   <1ms Local VPC   ┌────────────────────┐
│ Writable Primary │═════════►│ GCE VM: AD RODC        │◄──────────────────►│ Cloud Run Job      │
│ Domain Controller│  AD Repl │ rodc-gcp.corp.internal │   LDAPS TCP 636    │ (gcds-runner)      │
└──────────────────┘          └────────────────────────┘                    └────────────────────┘
```

### Why Admins Love the GCP RODC Pattern for GCDS
1. **Massive Sync Speedup**: GCDS issues hundreds or thousands of paged LDAP queries (`SimplePagedResultsControl`) when enumerating nested groups and organizational units. Over a 40ms WAN VPN, sequential LDAP round-trips compound; against a same-region GCE RODC (`<0.5ms`), sync times frequently drop from 20+ minutes to under 90 seconds.
2. **Zero Writable AD Secrets in the Cloud**:
   * An RODC holds a **read-only** replica of directory attributes (Users, Groups, OUs, Email, EmployeeID)—which is *everything* GCDS needs!
   * Configure an ** empty Password Replication Policy (PRP)** on the RODC so **zero user password hashes** are ever replicated into GCP.
3. **Survives WAN Maintenance**: If your office ISP or VPN tunnel goes down for maintenance, scheduled Cloud Run GCDS jobs continue reading cleanly from the local RODC without throwing connection errors or empty-result panics.
4. **Overlay Networking Alternative (If IPsec Cloud VPN Isn't Available)**: If your on-premises network sits behind CGNAT or lacks an enterprise IPsec router, the GCE RODC (or a lightweight subnet router VM in the VPC) can maintain an outbound encrypted WireGuard / Tailscale / ZeroTier tunnel to on-prem AD while exposing standard private VPC routing to Cloud Run.

## Option C: Google Cloud Managed Service for Microsoft AD

If your organization already uses **Google Cloud Managed Microsoft AD** (either as your primary directory or connected via a one-way/two-way forest trust to on-premises AD):
1. Configure **Authorized Networks** (VPC Peering) between Managed Microsoft AD and the VPC used by your Cloud Run Job.
2. Ensure `--vpc-egress=private-ranges-only` is set on the Cloud Run Job (already configured in `deploy/cloud-run/deploy.sh`).
3. Download your Managed Microsoft AD domain's LDAPS CA certificate (`gcloud active-directory domains describe ...`) and supply it via `AD_CA_CERT_PEM` (below).

---

## Trusting Your Internal Active Directory LDAPS Certificate (`AD_CA_CERT_PEM`)

Most Active Directory deployments sign Domain Controller LDAPS certificates using an internal **Active Directory Certificate Services (AD CS)** Root CA rather than a public CA (like Let's Encrypt or DigiCert).

Because GCDS runs on Java, an untrusted internal Root CA causes `PKIX path building failed: SunCertPathBuilderException` on port `636` or `3269`.

`gcds-in-the-cloud` automates this in RAM on every container run—no custom Docker image rebuilds needed:

1. Export your AD CS Root CA public certificate in Base64 PEM format (`ad-root-ca.pem`).
2. Store it in **Secret Manager**:
   ```bash
   gcloud secrets create gcds-ad-ldaps-ca \
     --data-file=ad-root-ca.pem \
     --project="$PROJECT_ID"

   gcloud secrets add-iam-policy-binding gcds-ad-ldaps-ca \
     --member="serviceAccount:gcds-sync@${PROJECT_ID}.iam.gserviceaccount.com" \
     --role="roles/secretmanager.secretAccessor" \
     --project="$PROJECT_ID"
   ```
3. Attach `AD_CA_CERT_PEM=gcds-ad-ldaps-ca:latest` to the Cloud Run Job:
   ```bash
   gcloud run jobs update gcds-runner \
     --update-secrets="AD_CA_CERT_PEM=gcds-ad-ldaps-ca:latest" \
     --region="$REGION" --project="$PROJECT_ID"
   ```
   At startup, `entrypoint.sh` automatically imports `AD_CA_CERT_PEM` into GCDS's ephemeral `/dev/shm/cacerts` truststore!

## Least-Privilege Active Directory Bind Account

Your AD bind account (`<authUser>` in `sync-config.xml`) **never** needs Domain Admin rights:
* Create a dedicated standard AD user (e.g., `CN=svc-gcds,OU=Service Accounts,DC=corp,DC=example,DC=com`) with a strong 32+ character password stored in Secret Manager (`gcds-ldap-password`).
* Default **Domain Users** read permissions are sufficient for standard user/group/OU attributes unless you have locked down custom confidential attributes via custom AD ACLs.
