# 4. Day-2 Operations and Scheduling

Once `gcds-runner` is deployed on Cloud Run Jobs, everyday administration can be performed entirely from the **Google Cloud Console browser UI** or simple `gcloud` commands—no RDP/SSH sessions required.

---

## 1. Scheduling Automated Syncs with Cloud Scheduler

Keep the Cloud Run Job's default environment variable as `SYNC_MODE=simulate` (so accidental manual clicks in the UI are always safe dry-runs!), and have **Cloud Scheduler** pass `SYNC_MODE=apply` when running scheduled production syncs.

### Grant Cloud Scheduler Permission to Invoke the Job
```bash
export PROJECT_ID="your-gcp-project"
export REGION="us-central1"
export SA_EMAIL="gcds-sync@${PROJECT_ID}.iam.gserviceaccount.com"

gcloud run jobs add-iam-policy-binding gcds-runner \
  --region="$REGION" \
  --member="serviceAccount:${SA_EMAIL}" \
  --role="roles/run.invoker" \
  --project="$PROJECT_ID"
```

### Create an Hourly Production Sync Schedule
```bash
gcloud scheduler jobs create http gcds-hourly-sync \
  --location="$REGION" \
  --schedule="0 * * * *" \
  --uri="https://${REGION}-run.googleapis.com/apis/run.googleapis.com/v2/projects/${PROJECT_ID}/locations/${REGION}/jobs/gcds-runner:run" \
  --http-method="POST" \
  --headers="Content-Type=application/json" \
  --message-body='{
    "overrides": {
      "containerOverrides": [{
        "env": [
          {"name": "SYNC_MODE", "value": "apply"},
          {"name": "CONFIG_URI", "value": "gs://'"${PROJECT_ID}"'-gcds-configs/sync-config.xml"}
        ]
      }]
    }
  }' \
  --oauth-service-account-email="$SA_EMAIL" \
  --project="$PROJECT_ID"
```

## 2. Running Multiple GCDS Configs on a Single Cloud Run Job

Many larger Workspace organizations split directory sync into multiple independent GCDS XML files—for example:
* `gs://<project>-gcds-configs/employees.xml` *(every 30 minutes)*
* `gs://<project>-gcds-configs/groups.xml` *(every hour)*
* `gs://<project>-gcds-configs/contractors.xml` *(every 4 hours)*

You **do not** need separate containers or separate Cloud Run Jobs. Simply upload all `.xml` files into `gs://<project>-gcds-configs/` and create separate Cloud Scheduler triggers (or manual executions) passing the desired `CONFIG_URI` override!

## 3. Testing Config Changes Safely (Cloud Console UI)

Whenever an admin wants to change an LDAP query or Org Unit mapping:

1. Upload the candidate file (e.g., `employees-v2.xml`) to `gs://<project>-gcds-configs/` in the Cloud Console.
2. Go to **Cloud Run -> Jobs -> `gcds-runner`** -> click **Execute -> Execute with overrides**.
3. Under **Environment variables**, set:
   * `CONFIG_URI` = `gs://<project>-gcds-configs/employees-v2.xml`
   * `SYNC_MODE` = `simulate`
4. Click **Execute** and inspect the **Logs** tab to review every proposed user/group change before promoting `employees-v2.xml` to `employees.xml`.
5. **Instant Rollback**: Because bucket versioning is enabled on `gs://<project>-gcds-configs`, you can restore any historical version of `sync-config.xml` under the **Versions** tab in Cloud Storage.

## 4. Cloud Monitoring Alerts (Replacing Legacy GCDS SMTP)

Instead of maintaining an SMTP relay for GCDS failure emails, create a native **Cloud Monitoring Alert Policy** that pages Slack, Google Chat, PagerDuty, or email whenever a Cloud Run Job execution fails (`sync-cmd` exits non-zero when safety limits trip or LDAP/API errors occur):

1. Open **Google Cloud Console -> Monitoring -> Alerting -> Create Policy**.
2. Select metric: **`Cloud Run Job` -> `Job` -> `Completed execution count`** (`run.googleapis.com/job/completed_execution_count`).
3. Add filter: `job_name = gcds-runner` AND `result = failed`.
4. Set threshold: **Any time series violates > 0** -> attach your Notification Channels (Email, Slack, Google Chat, PagerDuty).

## 5. Rotating the Active Directory Bind Password

When you rotate the password for your AD service account (`svc-gcds`):
1. Update the password in Active Directory.
2. Add a new version to Secret Manager:
   ```bash
   printf '%s' 'NEW_ROTATED_AD_PASSWORD' | \
     gcloud secrets versions add gcds-ldap-password --data-file=- --project="$PROJECT_ID"
   ```
That's it—the very next `gcds-runner` execution automatically pulls `latest` from Secret Manager and encrypts it into `/dev/shm/sync-config.xml` at boot.

---

## 6. Updating GCDS When Google Releases a New Version

Because `deploy/cloud-run/Dockerfile` pulls the latest official Linux 64-bit GCDS installer directly from `https://dl.google.com/dirsync/dirsync-linux64.sh`, upgrading GCDS is a single rebuild command:

```bash
gcloud builds submit \
  --config=deploy/cloud-run/cloudbuild.yaml \
  --substitutions="_IMAGE=${REGION}-docker.pkg.dev/${PROJECT_ID}/gcds-cloud/gcds-runner:latest" \
  --project="${PROJECT_ID}" .
```
